# 游戏测试用例 Excel 生成（V7.2-SLG强化版）

## 1. 技能概述

根据游戏系统策划文档（Excel/PDF/Word），按标准化11列模板批量生成结构化测试用例，输出带完整样式的Excel文件（.xlsx）。面向SLG项目时，额外强化世界地图、行军状态机、联盟协作、战斗结算、赛季/KVK、跨服合服、资源经济守恒、BUFF叠加与配置表组合校验。

### 2.1 输入预分析（生成前必做）

拿到文档后，先回答以下问题再动笔，避免后期大量补充：

1. **该系统是否涉及真实货币/内购？** → 是则必须覆盖付费专项（S8）
2. **该系统是否有排行榜或竞技排名？** → 是则 H3 排行榜容灾升级为高优先级
3. **该系统是否跨服/跨区？** → 是则 H4 + S3/S4 必选
4. **该系统是否有概率产出（抽卡/掉落/随机）？** → 是则必须覆盖 S10
5. **该系统是否限时/有时间窗口？** → 是则必须覆盖活动类专项
6. **该系统是否有新手引导/教程覆盖？** → 是则必须覆盖 S9
7. **该系统配置表有多少张？关键字段有哪些？** → 决定 CFG 模块深度
8. **该系统与哪些已有系统存在数据交互？** → 决定联动测试范围
9. **是否涉及世界地图、坐标、迁城、资源点、NPC、关卡、迷雾？** → 是则必须覆盖 G1 大地图与坐标系统
10. **是否涉及部队状态流转（待命/行军/采集/驻防/集结/战斗/返回/治疗）？** → 是则必须覆盖 G2/G3/G4 状态机
11. **是否涉及联盟权限、联盟建筑、联盟科技、联盟领土？** → 是则必须覆盖 G5 与联盟权限矩阵
12. **是否涉及赛季制、KVK、王国匹配、战区分组？** → 是则必须覆盖 G7 赛季/KVK专项
13. **是否涉及合服、迁服、转服、出生州/阵营切换？** → 是则必须覆盖 G8 合服迁服专项
14. **是否涉及多来源属性加成（科技/装备/英雄/皮肤/联盟/活动/道具）？** → 是则必须覆盖 G9 BUFF/属性/战力专项
15. **是否涉及战斗回放、战报、伤兵、死兵、治疗、复活？** → 是则必须覆盖 G3 战斗结算/战报一致性
16. **是否涉及定时器（建筑/训练/研究/采集/行军/活动结算）？** → 是则必须覆盖 G10 定时任务与离线结算
17. **是否涉及资源保护、掠夺、仓库容量、负数防护？** → 是则必须覆盖 G6 资源经济闭环
18. **是否涉及离线收益、服务器维护补偿、异常补发？** → 是则必须覆盖 H6/G10/GM补发链路

### 3.3 自测列与冒烟用例标记规范

#### 3.3.1 设计目的

「冒烟测试」列（J列）用于标记程序员在**提测前必须自行验证**的冒烟用例。标记为「是」的用例集合即为该系统的**冒烟测试集**，目的是：

- 程序提测前自查核心路径是否跑通，减少「一轮提测即打回」
- QA收到提测后可先快速执行自测标记用例，15分钟内判定是否达到可测标准
- 回归测试时优先执行自测标记用例，快速确认主干无损

#### 3.3.2 冒烟用例判定规则

满足以下**任一**条件的用例标记为冒烟测试（冒烟测试=「是」）：

| 序号 | 判定条件       | 具体标准                        | 示例                             |
| -- | ---------- | --------------------------- | ------------------------------ |
| ①  | 核心主路径正向验证  | 用例类型=「功能正常」 且 优先级=「紧急」或「高」  | 验证点击入口正常进入系统；验证资源充足时建造成功       |
| ②  | 系统入口可达性    | 所属模块为入口/开启类 且 用例类型=「功能正常」   | 验证达到等级后入口显示；验证首次进入触发引导         |
| ③  | 关键资源操作正向链路 | 涉及货币/道具/资源的正向扣减、发放、收取操作     | 验证收取收益金币到账正确；验证升级扣减资源正确        |
| ④  | 核心状态流转主路径  | 用场景法/状态迁移法设计的完整主流程用例        | 验证完整事件链A→B→C→D按序执行             |
| ⑤  | 配置表基础可用性   | 配置表ID唯一性、外键引用存在性等基础校验       | 验证商铺配置表ID唯一且无空行                |
| ⑥  | SLG最小主循环   | SLG系统的核心闭环能在提测前跑通           | 验证建筑升级→资源扣减→部队派遣→战斗/采集→奖励/战报产出 |
| ⑦  | SLG关键状态恢复  | 行军、建筑、训练、治疗、赛季入口等核心状态重登后可恢复 | 验证行军中断线重登后部队状态与剩余时间正确          |

#### 3.3.3 不标记为冒烟测试的用例

以下类型**明确不标记**，但SLG核心状态恢复用例如属于主链路可例外标记：

| 排除类型                | 原因                    |
| ------------------- | --------------------- |
| 用例类型=功能异常/边界值       | 属于异常分支和极端场景，非冒烟范畴     |
| 用例类型=性能/兼容/安全/压力弱网  | 属于专项测试，需专门环境和工具       |
| 优先级=「低」             | 视觉细节和极端边缘case不影响核心可用性 |
| 用例类型=UI交互 且 优先级≠「高」 | UI细节不影响功能可用           |
| 仅含服务端免疫/安全攻防的验证     | 需要抓包工具等特殊环境，程序自测不便执行  |

#### 3.3.4 冒烟比例参考

健康的冒烟用例占比约为总用例的 **20%\~35%**：

- < 15%：冒烟集过薄，可能遗漏核心路径，需检查是否有高优正向用例未标记
- 15%\~35%：合理区间
- \> 40%：冒烟集过厚，失去「快速验证」意义，需检查是否把异常/边界用例误标

SLG项目的冒烟集合必须覆盖最小主循环（按系统适用性选择）：登录进城→核心入口→建筑/训练/研究任一队列→资源扣减/发放→部队派遣/召回→一次PVE或PVP战斗→战报/奖励产出→重登状态恢复。

## 5. 用例覆盖体系（V7.0 四层规则）

所有系统用例必须覆盖以下四层，缺一不可。生成后执行强制去重与覆盖率审计。

### 5.1 第一层：8大横向专项维度

每个系统均需覆盖：

| 编号 | 维度       | 核心检查点                                                       |
| -- | -------- | ----------------------------------------------------------- |
| H1 | 多玩家状态矩阵  | 同一功能在不同玩家状态（新号/老号/满级/未解锁/封禁/VIP等级/付费/非付费/回流玩家等）下的表现         |
| H2 | 账号切换与多设备 | 切换账号后数据隔离、缓存清理、状态重置；**同一账号多设备同时登录挤号逻辑、数据以哪端为准**             |
| H3 | 排行榜容灾    | 排行榜数据异常、空榜、并列排名处理、跨时区刷新、回档后排名恢复、**满榜性能、排名追溯**               |
| H4 | 跨服数据     | 跨服场景下数据同步、延迟、冲突、回传；**合服后数据合并冲突、跨服邮件/聊天**                    |
| H5 | 服务端免疫    | 客户端篡改请求、重复提交、变速齿轮、封包重放、**时间戳校验、请求签名校验、频率限制**                |
| H6 | 奖励发放     | 奖励重复领取、背包满时发放、邮件补发、跨天/跨周重置边界、**奖励溢出处理（超过数值上限）、多渠道同时发放同一奖励** |
| H7 | 并发与竞态    | **双端/多端同时操作同一资源、快速连续点击重复请求、分布式锁校验、库存超卖/超领、乐观锁冲突处理、操作幂等性**   |
| H8 | 数据持久化与回档 | **存档完整性、断电/闪退后数据恢复、服务端回档后客户端状态同步、增量存档与全量存档、数据版本迁移兼容**       |

### 5.2 第二层：10大系统级参考要点

根据系统类型选取适用项（至少覆盖3项）：

| 编号  | 要点          | 适用系统类型        | 核心检查点                                                                                       |
| --- | ----------- | ------------- | ------------------------------------------------------------------------------------------- |

### 5.4 UI交互8维度

每个系统的界面交互必须覆盖：

1. **正常操作流程**：按钮点击、页面跳转、数据提交的完整正向路径
2. **异常/中断操作**：操作过程中断网、闪退、切后台、来电中断后恢复、**锁屏后解锁恢复**

### 5.5 活动类系统专项

活动类型系统额外覆盖6项：

1. **时间边界**：开启前/开启瞬间/进行中/结束瞬间/结束后各时间节点；**跨天23:59:59→00:00:00瞬间；服务器时间与客户端时间不一致；调整系统时间**

5. **入口与跳转**：活动入口显示/隐藏、跳转链接、活动结束后入口处理；**深链接/Push通知跳转到已结束活动的容错**

#### 5.11.1 SLG状态机强制建模

以下对象如在文档中出现，必须生成状态迁移类用例，覆盖正常流转、非法跳转、中断恢复、重复提交：

| 对象       | 标准状态链                       | 必测异常                             |
| -------- | --------------------------- | -------------------------------- |
| 部队       | 空闲→行军→战斗/采集/驻防→返回→空闲        | 行军中再次派出、目标消失、召回瞬间战斗、服务器重启、跨服返回失败 |
| 集结       | 创建→加入→等待→发车→战斗→解散           | 发车瞬间退出联盟、队员掉线、兵力不足、集结目标迁城、集结超时   |
| 建筑       | 可建造→建造中→可加速→完成→升级中          | 完成瞬间加速、资源不足、前置建筑变化、拆除/降级/重置      |
| 训练/研究/治疗 | 开始→进行中→加速→完成→领取             | 队列满、加速重复扣、完成未领取跨天、取消返还           |
| 联盟成员     | 申请→成员→官员→盟主→退出/踢出           | 盟主转让中解散、踢出驻防成员、权限变更后旧权限残留        |
| 赛季       | 未开启→预告→报名→匹配→进行中→结算中→已结束→清档 | 结算中提交积分、未领奖结束、跨服回传失败、清档遗漏        |

#### 5.11.2 SLG资源经济守恒原则

所有资源、道具、货币、兵力、积分、次数类用例必须验证：

- 操作前数量、消耗数量、获得数量、操作后数量四者一致
- 操作失败时不扣资源、不消耗道具、不推进队列、不改变状态
- 回滚、取消、召回、中断后返还数量准确，不多返、不少返
- 快速连点、双端操作、弱网重试、服务端重放时具备幂等性
- 仓库保护、掠夺上限、资源容量、邮件补发、数值上限不产生负数或溢出
- 加速类操作必须校验剩余时间、免费加速阈值、VIP/活动/道具加速叠加结果

#### 5.11.3 SLG战斗结算与战报一致性原则

战斗类用例必须至少校验以下三方一致：服务端结算数据、客户端战报展示、玩家资产变化。重点覆盖：

- 攻防双方兵力、伤兵、死兵、治疗队列、复活队列变化
- 击杀、战功、积分、活动任务、排行榜贡献归属
- 英雄、装备、科技、联盟、城池、地形、天气、临时道具、赛季技能等BUFF是否生效
- 双方查看同一战报、分享战报、回放战报时数据一致
- 战斗中断线、重登、跨服回传延迟、服务器重启后结算不可被二次触发

#### 5.11.4 赛季/KVK专项规则

赛季/KVK系统必须覆盖：报名资格、匹配分组、出生点、迁服限制、跨服地图进入/退出、赛季科技/技能/货币/商店继承或清档、赛季任务、赛季排行榜锁榜、并列排名、奖励补发、未领奖处理、赛季结束入口隐藏、跨服数据回传、本服回归、维护延长补偿、新旧客户端进入赛季服兼容。

#### 5.11.5 合服/迁服专项规则

合服/迁服系统必须覆盖：玩家同名、联盟同名、坐标重排、城池/资源点/联盟建筑/关卡归属、排行榜重算、邮件/战报/聊天/好友/黑名单/收藏迁移、进行中的行军/采集/建筑/训练/研究/治疗处理、活动进度与排行榜合并、充值/月卡/订阅/礼包限购迁移、红点/任务/成就重复触发防护。

## 6. 用例编写要求

### 6.1 用例标题

- 动宾结构，简明扼要，不超过30字
- 体现测试意图：正常验证/异常校验/边界测试
- **含否定条件时明确写出**：不要写"验证异常情况"，要写"验证等级不足时爬塔入口置灰不可点击"
- **示例**：
  - 正向："验证首次通关副本正确发放三星奖励"
  - 反向："验证背包已满时购买道具提示失败并不扣除货币"
  - 边界："验证道具数量恰好达到999上限时继续获取的溢出处理"

### 6.2 执行步骤

- 每步一个动作，编号递进
- 明确操作对象和输入数据
- 避免模糊描述（如"随便输入"→"输入包含emoji的30字符文本"）
- **环境/数据准备步骤单独列出**，不与操作步骤混在一起
- **关键等待/确认点明确标注**（如"等待服务端返回结果约2s"）

### 6.3 预期结果

- 可验证、可判定，避免"正常显示"等模糊表述
- 明确UI表现+数据变化+状态变化，**三者缺一不可**（如适用）
- 多预期按步骤对应或用分号分隔
- **量化描述**：不说"加载很快"，说"加载耗时≤2s"
- **包含否定预期**：不仅写"应该发生什么"，还写"不应该发生什么"（如"货币不扣减；背包数量不变"）
- **示例**：
  - 弱："按钮正常显示"
  - 强："按钮显示为灰色不可点击；点击后无响应（无弹窗、无跳转）；按钮上方提示文字显示'等级不足，需达到10级'；提示3秒后自动消失"

### 6.4 优先级判定标准（4级风险矩阵）

| 优先级 | 判定标准                                | 典型场景                       |
| --- | ----------------------------------- | -------------------------- |
| 紧急  | **涉及真实货币损失、数据不可逆损坏、大规模玩家影响、法律合规风险** | 支付扣款但不到账、存档丢失、概率不合规、个人信息泄露 |
| 高   | 核心功能主路径、资金/数据安全、崩溃/闪退风险、服务端校验       | 核心玩法卡死、奖励重复发放、服务端校验缺失      |
| 中   | 次要功能、异常分支、边界值、UI交互主要场景              | 非核心界面布局异常、边界值处理、次要功能报错     |
| 低   | 视觉细节、极端边缘场景、提示文案、非关键兼容              | 文案错别字、极低概率触发的边缘case、视觉微调   |

**风险矩阵判定法**：当不确定优先级时，用「影响范围 × 发生概率 × 损失严重度」三维评估：

- 影响范围：全服 > 部分玩家 > 个别玩家
- 发生概率：必现 > 高概率 > 低概率 > 极端条件
- 损失严重度：资金损失/数据丢失 > 功能不可用 > 体验差 > 视觉瑕疵

**优先级分布参考**：一组健康的用例集优先级分布约为 紧急5% / 高25% / 中45% / 低25%，偏差过大应复审。

### 6.5 前置条件标准化（V7.0新增）

前置条件必须具体到可操作，避免"环境正常"等废话：

| 反例       | 正例                                |
| -------- | --------------------------------- |
| "环境正常"   | "服务端已部署v2.3.1；客户端为v2.3.1-hotfix2" |
| "有足够资源"  | "背包内金币≥10000；钻石≥500"              |
| "玩家等级满足" | "角色等级≥30级；已完成主线任务第3章"             |
| "活动已开启"  | "当前时间在活动配置的开启时间之后；活动状态为'进行中'"     |
| 无        | 确实无前置条件时填"无"，不留空                  |

### 6.6 反向用例设计原则（V7.0新增）

每个正向用例应考虑至少一个对应的反向/异常用例。常见反向设计模式：

| 正向场景     | 对应反向场景            |
| -------- | ----------------- |
| 满足条件可执行  | 不满足条件被拦截（且给出正确提示） |
| 操作成功扣减资源 | 操作失败不扣减资源（原子性）    |
| 正常流程完成   | 流程中任意步骤中断后的恢复/回滚  |
| 单次操作成功   | 重复/并发操作的幂等性       |
| 在有效期内操作  | 过期/未开始时操作被拒绝      |
| 权限内操作    | 越权操作被拦截并记录        |

### 6.7 数据驱动用例模板（V7.0新增）

对于输入组合多的场景（如多条件判定），使用数据驱动格式减少冗余：

在执行步骤中写明参数化：

```
1. 设定角色等级为{LEVEL}
2. 设定VIP等级为{VIP}
3. 进入商店页面
4. 查看折扣价格
```

在备注列用表格标注数据集：

```
数据集: LEVEL=1,VIP=0→原价 | LEVEL=30,VIP=3→9折 | LEVEL=60,VIP=10→7折
```

这样一条用例可覆盖多组输入，避免大量步骤雷同的用例占据篇幅。

## 7. 去重与质量校验规则（强制执行）

生成用例后必须执行以下10项校验：

1. **标题去重**：同一模块内用例标题不得完全重复
2. **步骤去重**：不同模块间测试步骤+预期结果高度相似（>80%）的合并
3. **覆盖完整性**：核对5.1\~5.6各维度是否均有用例覆盖（生成覆盖矩阵）
4. **编号连续性**：模块代码下序号连续无断号
5. **模块归属**：每条用例必须归属且仅归属一个模块
6. **类型一致性**：用例类型与测试内容匹配（如性能测试用例不应标记为"功能正常"）
7. **覆盖率审计（V7.0新增）**：生成覆盖率报告，列出每个维度的用例数量，标记0覆盖维度为⚠️
8. **优先级分布校验（V7.0新增）**：检查优先级分布是否合理（紧急≤10%、高20-30%、中40-50%、低20-30%），偏差过大需复审
9. **前置条件可执行性（V7.0新增）**：抽查前置条件，确保测试人员可根据描述独立准备环境，无需口头沟通
10. **SLG专项覆盖校验（V7.2-SLG新增）**：SLG系统必须审计G1\~G10适用项；不适用项需说明豁免原因；付费、跨服、合服、赛季、战斗、联盟权限、经济资源类不得无理由豁免

### 7.1 覆盖矩阵输出格式

去重校验完成后，在 JSON 文件同目录生成一份覆盖率摘要（输出到控制台即可），格式：

```
=== 覆盖率审计报告 ===

第一层横向专项(8项):
  H1 多玩家状态矩阵: 5条 ✓
  H2 账号切换与多设备: 3条 ✓
  ...
  H8 数据持久化与回档: 0条 ⚠️ 缺失！

第二层系统级要点(选取X项/共10项):
  S2 活动: 8条 ✓
  ...

第三层传统专项(6项):

  G1 大地图与坐标系统: 6条 ✓

  ...

第四层方法论驱动:
  等价类: 12条 | 边界值: 8条 | 判定表: 4条 | 状态迁移: 3条 | 场景法: 5条 | 错误推测: 6条
```

## 8. 生成流程

```
1. 输入预分析（2.1节18问）
   ├── 回答18个预判问题
   ├── 确定必选专项范围
   ├── 若为SLG/含SLG机制，识别G1~G10适用项
   └── 识别需要深度覆盖的高风险模块

2. 解析策划文档
   ├── 提取系统名称、类型标签
   ├── 提取核心规则、界面说明、数值配置
   ├── 识别关联系统和特殊机制
   └── 提取配置表结构（字段名/类型/取值范围）

3. 模块划分
   ├── 按功能域拆分模块（参考3.2命名规范）
   ├── 确定模块代码
   ├── 估算各模块用例数量
   └── 标记高风险模块（需加密覆盖）

4. 逐层生成用例
   ├── 功能正常/异常/边界用例（基于策划规则）
   ├── 第一层：8大横向专项维度
   ├── 第二层：10大系统级参考要点（按类型选取≥3项）
   ├── 第三层：6大传统专项
   ├── 第四层：经典方法论驱动（每模块≥3种方法）
   ├── SLG专项覆盖层（如为SLG/含SLG机制，按G1~G10适用项覆盖）
   ├── UI交互8维度
   ├── 活动类追加专项（如适用）
   ├── 付费专项（如适用）
   ├── 配置表深度校验
   ├── GM/运营测试（如适用）
   └── 系统间联动用例（如有关联系统）

5. 反向用例补全
   ├── 逐条正向用例检查是否有对应反向/异常用例
   └── 补充缺失的反向用例

6. 冒烟用例标记（3.3节规则）
   ├── 按5条判定规则逐条标记自测=「是」
   ├── 校验冒烟比例在20%~35%区间
   └── 比例异常时复审标记（过高则收紧、过低则补充）

7. 去重与质量校验
   ├── 执行第7节全部10项校验
   ├── 输出覆盖率审计报告
   ├── 标记并合并重复用例
   └── 补充覆盖缺失的维度

8. 输出Excel
   ├── 按第4节样式规范生成（含自测列样式）
   ├── 添加数据验证和条件格式
   └── 输出到指定路径
```

## 9. 工作流（执行步骤）

### Step 0: 输入预分析（V7.0新增）

1. 阅读用户提供的文档
2. 回答2.1节18个预判问题
3. 向用户确认系统类型和特殊要求（如不明确）
4. 确定本次生成必须覆盖的专项范围；若为SLG/含SLG机制，明确G1\~G10适用项与不适用项原因

### Step 1: 理解需求并拆解模块

1. 阅读用户提供的需求文档/设计文档/功能描述
2. 识别系统类型（活动/养成/跨服/社交/战斗/商店/付费/抽卡等）
3. 拆解为测试模块和功能点
4. 为每个模块分配3位大写字母缩写（用于用例编号）
5. 标记高风险模块和关联系统

### Step 2: 按四层覆盖体系设计测试用例

按第5节覆盖体系为每个功能点设计用例，确保：

- 第一层8大横向专项全部覆盖
- 第二层系统级要点按类型选取≥3项
- 第三层6大传统专项全部覆盖
- 第四层每模块至少运用3种测试方法论
- SLG专项覆盖层G1\~G10按适用性覆盖；不适用项必须说明原因
- UI交互8维度覆盖
- 活动类系统追加专项（如适用）
- 付费专项（如涉及真实货币）
- 配置表深度校验
- GM/运营专项（如适用）
- 系统间联动用例（如有关联系统）

### Step 3: 反向用例补全

1. 逐条审视正向用例，补充对应反向/异常用例
2. 对付费相关用例重点审查原子性和回滚测试
3. 对并发场景补充竞态条件用例
4. 对SLG资源/兵力/积分/次数类用例补充经济守恒校验
5. 对SLG状态机对象补充非法跳转、中断恢复、重复提交用例

### Step 4: 冒烟用例标记（V7.1新增）

1. 按3.3.2节7条判定规则逐条扫描用例，符合任一条件的标记 self\_test=「是」
2. 计算冒烟比例：自测数 / 总用例数
3. 若比例 < 15%：检查是否有高优正向用例遗漏标记，补充标记
4. 若比例 > 40%：检查是否有异常/边界/专项用例误标，移除标记
5. SLG系统需检查冒烟集是否覆盖最小主循环：登录进城、核心入口、队列操作、资源变化、部队派遣/召回、战斗/采集、战报/奖励、重登恢复
6. 输出冒烟用例清单（编号+标题），供复审

### Step 5: 生成 JSON 数据

将所有用例写入 JSON 文件，格式如下：

```json
[
  {
    "id": "ENT_001",
    "self_test": "是",
    "module": "入口与开启条件",
    "case_type": "功能正常",
    "title": "验证VIP入口在主界面正确显示",
    "precondition": "功能默认开启；玩家已登录；角色等级≥10级",
    "steps": "1.登录游戏\n2.进入主界面\n3.查看右上角功能区",
    "expected": "1.登录成功进入主界面\n2.右上角显示VIP图标按钮\n3.按钮样式与UI设计稿一致；按钮可点击；点击后跳转VIP详情页",
    "priority": "高",
    "status": "未执行",
    "note": ""
  }
]
```

注意：

- `self_test` 冒烟用例填 `"是"`，非冒烟填空字符串 `""`
- `steps` 和 `expected` 多步用 `\n` 换行
- `status` 默认填 `未执行`
- `note` 无内容填空字符串
- 联动用例在 `note` 中标注 `[回归]关联XX系统`
- 数据驱动用例在 `note` 中标注数据集

### Step 6: 去重与覆盖率校验

执行第7节全部10项校验，确保：

- 标题无重复
- 步骤+预期无高度相似
- 四层覆盖体系完整
- 编号连续无断号
- 模块归属正确
- 类型一致
- 覆盖率审计通过（无⚠️缺失项）
- SLG专项覆盖通过；不适用项已写明原因
- 优先级分布合理
- 前置条件可执行

### Step 7: 生成 Excel

执行脚本生成格式化 Excel：

```bash
python3 <skill_dir>/scripts/generate_excel.py \
  --input cases.json \
  --output "XX系统测试用例.xlsx" \
  --sheet-name "XX系统测试用例"
```

脚本会自动应用：11列表头样式、自测列浅蓝底色+下拉验证（B列）、优先级颜色标记（I列）、执行状态下拉验证+条件格式（J列）、列宽、冻结首行、自动筛选、行高规范。

### Step 8: 质量检查

按第10节质量检查清单逐项确认，特别注意：

- 自测列标记是否符合3.3节规则
- 冒烟比例是否在20%\~35%区间
- 冒烟用例清单是否覆盖了系统核心主路径

### Step 9: 交付

通过 `present_files` 将生成的 .xlsx 文件交付给用户。

## 10. 质量检查清单

生成完成后逐项确认：

**格式与样式（7项）**

- ☐ 11列完整，列名和顺序正确（编号/自测/模块/类型/标题/前置/步骤/预期/优先级/状态/备注）
- ☐ 自测列样式正确：值为「是」时浅蓝底#BDD7EE加粗居中；下拉验证；列宽6
- ☐ 表头样式：蓝底白字加粗居中、行高40、冻结首行、自动筛选
- ☐ 数据行行高80、细边框、自动换行
- ☐ 优先级底色正确（紧急深红/高红/中黄/低绿，I列）
- ☐ J列下拉验证5选项（含阻塞），条件格式5色联动
- ☐ 文件可正常打开，无样式损坏

**编号与结构（3项）**

- ☐ 用例编号格式正确（{模块代码}\_{序号}）、连续无断号
- ☐ 每条用例归属且仅归属一个模块
- ☐ 用例类型与测试内容匹配

**覆盖完整性（13项）**

- ☐ 第一层8大横向维度全部覆盖
- ☐ 第二层系统级要点按类型选取≥3项
- ☐ 第三层6大传统专项全部覆盖
- ☐ 第四层方法论驱动：每核心模块≥3种方法
- ☐ UI交互8维度覆盖
- ☐ 活动类系统追加6项专项（如适用）
- ☐ 付费专项覆盖（如涉及真实货币）
- ☐ 配置表深度校验覆盖（如有配置表）
- ☐ 系统间联动用例覆盖（如有关联系统）
- ☐ SLG专项G1\~G10按适用性覆盖；不适用项已说明原因
- ☐ SLG状态机对象已覆盖正常流转、非法跳转、中断恢复、重复提交
- ☐ SLG资源/兵力/积分/次数类用例已覆盖经济守恒和负数/溢出防护
- ☐ SLG战斗用例已覆盖服务端结算、客户端战报、玩家资产变化三方一致

**冒烟用例（自测列）（4项）**

- ☐ 冒烟比例在20%\~35%区间（比例=自测「是」数量/总用例数）
- ☐ 所有冒烟用例均满足3.3.2节7条判定规则之一（无误标）
- ☐ 每个核心模块至少有1条冒烟用例（不存在核心模块零冒烟的情况）
- ☐ SLG系统冒烟集覆盖最小主循环（登录进城/核心入口/队列/资源/部队/战斗或采集/战报或奖励/重登恢复）

**质量与可执行性（4项）**

- ☐ 去重校验通过（10项全部通过）
- ☐ 预期结果可验证、无模糊表述（抽查≥10条）
- ☐ 前置条件具体可操作、无"环境正常"类废话（抽查≥10条）
- ☐ 优先级分布合理（紧急≤10%/高20-30%/中40-50%/低20-30%）

## 12. 常见遗漏场景速查表（V7.0新增）

资深测试工程师经验总结，以下场景在评审中最常被遗漏：

| 场景           | 为什么容易遗漏        | 导致的典型线上事故              |
| ------------ | -------------- | ---------------------- |
| 跨天/跨周/跨月零点操作 | 策划文档很少写零点边界    | 日常任务重置时正在提交导致数据异常      |
| 夏令时/时区切换     | 国内开发者不关注       | 海外服活动提前/延后1小时          |
| 合服后数据冲突      | 合服是运营操作非常规测试   | 合服后排行榜数据错乱、同名角色冲突      |
| 多活动同时开启      | 单活动测试时正常       | 两个活动共用同一货币导致互相扣减       |
| 订阅到期续费失败     | 测试环境难以模拟真实续费   | 月卡到期后权益未撤销             |
| 快速连点重复提交     | 功能测试时操作规范      | 一次点击发了两封邮件/领了两次奖励      |
| 配置表ID重复      | 策划手工填表易出错      | 读取到错误配置导致功能异常          |
| 引导中来电/闪退     | 引导路径很长，测中断点多   | 引导流程卡死无法继续游戏           |
| 背包满+邮件满同时发奖  | 单一容器满的测试做了     | 奖励彻底丢失无法找回             |
| 退款后道具未回收     | 退款是渠道触发非游戏内操作  | 玩家利用退款漏洞白嫖             |
| 热更新后旧缓存      | 热更测试通常从新安装开始   | 老玩家更新后显示旧资源/旧文本        |
| 弱网下支付        | 支付测试通常在好网络下做   | 支付成功但回调丢失导致掉单          |
| 部队卡死在行军中     | 行军状态链长且依赖定时任务  | 玩家无法召回/无法再次派兵，严重影响核心体验 |
| 集结发车瞬间成员退出   | 多人协作场景难构造      | 集结人数、兵力、战斗归属异常         |
| 战报与实际损兵不一致   | 只看战报不核对资产变化    | 玩家投诉战损异常、战斗可信度下降       |
| 联盟权限越权       | 权限矩阵组合多        | 普通成员执行官员/盟主操作，造成联盟资产损失 |
| 赛季结束结算中继续得分  | 结算锁榜窗口短        | 排名奖励错发、赛季积分不一致         |
| 合服后坐标冲突      | 合服流程测试成本高      | 城池、联盟建筑、资源点重叠或丢失       |
| BUFF过期未移除    | 属性刷新依赖多入口触发    | 战力虚高、战斗结果异常            |
| 仓库保护失效       | 掠夺规则与保护规则容易分开测 | 被攻击后保护资源被错误扣除          |
| 加速道具重复扣除     | 快速连点/弱网重试易遗漏   | 玩家道具损失或队列时间异常          |
| 排行榜延迟导致奖励错发  | 榜单展示与发奖源不一致    | 高价值排名奖励发错对象            |
| 迁服后数据缺失      | 迁移字段多且跨服务      | 邮件、战报、好友、充值、活动进度丢失     |
| 多活动共用道具冲突    | 活动联动关系文档常缺失    | 活动A消耗影响活动B进度或兑换        |
